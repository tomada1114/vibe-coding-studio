# ドキュメント更新の要否判断

**扱う:** ある変更のあとにドキュメント更新が要るかどうかの判断基準、更新するなら
どのファイルに書くかの振り分け。
**扱わない:** デザイン提案ドキュメントの中身そのもの（`geist-grid-design`）；
SKILL.md 自体の書き方（`authoring-skills`）；Issue 本文の書き方（`triaging-issues`）。

## 判断基準: 観測可能性

ドキュメント更新が要るかどうかは、**外から観測できる振る舞い・API・UI が変わったか**
で決める。実装の中身をどれだけ書き換えても、コンポーネントの内部実装だけを変える
リファクタリング・変数名の整理・依存の入れ替えのように、外部から見た挙動が変わらない
変更には、ドキュメント更新は要らない。

判断の目安:

- ページの表示内容・URL・コンポーネントの props・公開関数のシグネチャが変わった →
  更新が要る。
- セットアップ手順・コマンド・環境変数が変わった → 更新が要る。
- 実装方針・設計判断が変わり、あとで「なぜそうしたか」を追えなくなる → 更新が要る。
- 内部のファイル分割・命名・実装アルゴリズムだけが変わり、上記のいずれにも
  当てはまらない → 更新は要らない。

## 「更新不要」も正しい結論

このスキルの核心は、**「ドキュメント更新は不要」という判断自体が正しい結論に
なりうる**ことだ。変更のたびに何かしらドキュメントへ手を入れる必要はない。
観測可能性の基準に照らして当てはまるものがなければ、何も書かずに終えてよい。
「触ったからには何か書き足す」という逆方向の圧力の方が、ドキュメントを実体と
ずれさせる典型的な原因になる。

迷ったら、まず「この変更を知らない人が、外部からの見え方だけでこの変更に
気づけるか」を自問する。気づけないなら、更新は要らない。

## どの面に書くか

更新が要ると判断したら、内容の性質で書き先を決める。各ファイルの役割分担は
`AGENTS.md` の「ドキュメント・仕様」節が単一の情報源で、ここには複製しない。

### セットアップ手順

開発環境の立ち上げ方・コマンド・依存関係のインストール手順が変わったときは、
`README.md`（リポジトリ直下）または `docs/README.md`（ドキュメント一覧の入口）の
該当箇所を直す。

### プロジェクト全体・API・コンポーネントの説明

プロジェクト全体の構成、API の仕様、コンポーネントの使い方が変わったときは
`docs/PROJECT_DOCUMENTATION.md` / `docs/API_REFERENCE.md` / `docs/COMPONENT_GUIDE.md`
のいずれかに書く。どれに書くかは `AGENTS.md` の役割分担（全体 / API / コンポーネント）
にそのまま従う。

### デザインの根拠・意思決定の記録

デザイン上の判断理由や Decision ledger を残すときは、`docs/design/proposals/` に
提案ドキュメントを置く。`docs/design/proposals/2026-09-geist-grid.md` が根拠と
Decision ledger を持つ既存の実例で、このリポジトリでは新しいデザイン変更のたびに
新しい提案ファイルを作るのが慣習になっている（既存ファイルへの追記ではない）。
提案ドキュメントの中身の書き方そのものは `geist-grid-design` の範囲。

### プロダクト・技術・構造の方針

プロダクトの方向性、技術選定、ディレクトリ構造といった方針そのものが変わったときは
`.kiro/steering/product.md` / `tech.md` / `structure.md` を直す。

### 機能仕様

現状、進行中の機能仕様は無く `.kiro/specs/archive/` に完了分があるのみ。新しい
仕様が必要になったら `.kiro/specs/` に置くが、`/kiro:*` コマンドは削除済みなので
手動でファイルを作成・更新する。

## 触らないもの

`coverage/` や `.next/` のような生成物にはドキュメントを書かない。次のビルドや
テスト実行で消える。

スキルや `AGENTS.md` 自体の記述が誤っている・古いと気づいた場合、それ自体は
ドキュメントの変更だが、「SKILL.md の中身をどう編集するか」はこのスキルが扱う
『ドキュメント更新の要否判断』の対象ではなく `authoring-skills` の話。

## 運用のヒント

「このドキュメントは更新しなくてよいと判断した」という一言を PR の説明やコミット
メッセージに残しておくと、レビュアーが同じ判断を再度やり直さずに済む。特に、
変更が大きく見えるのにドキュメント差分が無い PR では有効。
