# Requirements: /videos アーキテクチャリファクタリング

## 1. プロジェクト概要

### 1.1 目的

`/videos`機能のアーキテクチャを、クリーンアーキテクチャ + 軽量DDDに基づいてリファクタリングし、メンテナンス性、拡張性、テスタビリティを大幅に向上させる。

### 1.2 背景

現状の実装は突貫工事的に作られたため、以下の課題があります：

- **レイヤー分離の不明瞭さ**: データアクセス、ビジネスロジック、ドメインロジックが混在
- **依存関係の複雑さ**: 直接importによる密結合、テスタビリティの低下
- **ドメインモデルの欠如**: DTOのみでビジネスルールがエンティティに含まれていない
- **責務の不明瞭さ**: 機能の境界が曖昧で、変更の影響範囲が広い

### 1.3 スコープ

**対象範囲:**
- `src/lib/videos/` - ビジネスロジック層全体
- `src/data/videos/` - 動画データファイル（29本）
- `src/app/videos/` - プレゼンテーション層
- `src/components/videos/` - UIコンポーネント
- `scripts/generate-indexes.ts` - インデックス生成スクリプト
- `scripts/validate-indexes.ts` - インデックス検証スクリプト

**対象外:**
- Udemy関連機能（別仕様で対応予定）
- UIデザインの変更
- パフォーマンス最適化（現状維持が前提）

## 2. 機能要件

### 2.1 既存機能の完全互換性（必須）

#### FR-001: 動画一覧取得
- **説明**: すべての動画データを取得できる
- **現状API**: `getAllVideos(): VideoMetadata[]`
- **要件**: 既存のパブリックAPIが同じシグネチャで動作すること

#### FR-002: 最新動画一覧取得
- **説明**: 公開日順（新しい順）でソートされた動画データを取得できる
- **現状API**: `getLatestVideos(): VideoMetadata[]`
- **要件**: 既存のパブリックAPIが同じシグネチャで動作すること

#### FR-003: 動画ID検索
- **説明**: 動画IDから動画データを取得できる
- **現状API**: `getVideoById(id: string): VideoMetadata | undefined`
- **要件**: 既存のパブリックAPIが同じシグネチャで動作すること

#### FR-004: 動画ID一覧取得
- **説明**: すべての動画IDを取得できる（Next.js generateStaticParams用）
- **現状API**: `getAllVideoIds(): string[]`
- **要件**: 既存のパブリックAPIが同じシグネチャで動作すること

#### FR-005: 関連動画検索
- **説明**: タグベースのスコアリングアルゴリズムで関連動画を検索できる
- **現状API**: `findRelatedVideos(tags: string[], currentVideoId?: string): RelatedVideo[]`
- **要件**:
  - 既存のパブリックAPIが同じシグネチャで動作すること
  - スコアリングアルゴリズムが現状と同等の結果を返すこと
  - 上位3-5本の関連動画を返すこと

#### FR-006: インデックス生成
- **説明**: 動画データからインデックスファイルを生成できる
- **現状スクリプト**: `npm run generate:indexes`
- **要件**:
  - スクリプトが正常に実行できること
  - `src/data/indexes/video-index.json`が生成されること
  - 生成されたインデックスの形式が現状と互換性があること

#### FR-007: インデックス検証
- **説明**: インデックスファイルの存在と形式を検証できる
- **現状スクリプト**: `npm run validate:indexes`
- **要件**:
  - スクリプトが正常に実行できること
  - インデックスの形式検証が正しく動作すること

### 2.2 新規機能要件

#### FR-101: ドメインモデルの導入
- **説明**: ビジネスルールをエンティティに含める
- **要件**:
  - Videoエンティティの作成
  - 値オブジェクト（VideoId, Tags, PublishedAt等）の作成
  - ビジネスルールのカプセル化

#### FR-102: リポジトリパターンの導入
- **説明**: データアクセスを抽象化する
- **要件**:
  - `IVideoRepository`インターフェースの定義
  - 静的データソース用リポジトリ実装
  - インデックスベース検索用リポジトリ実装

#### FR-103: ユースケース/クエリの分離
- **説明**: アプリケーションロジックを明確に定義する
- **要件**:
  - 各機能をユースケース/クエリとして実装
  - CQRS的なアプローチ（読み取り専用クエリの分離）

## 3. 非機能要件

### 3.1 パフォーマンス要件

#### NFR-001: レスポンス時間維持
- **要件**: すべてのAPI呼び出しが現状と同等またはそれ以上の速度で動作すること
- **測定基準**:
  - `getAllVideos()`: 10ms以内
  - `getVideoById()`: 5ms以内
  - `findRelatedVideos()`: 50ms以内

#### NFR-002: ビルド時間維持
- **要件**: Next.jsのビルド時間が現状の±10%以内であること
- **測定基準**: `npm run build`の実行時間

#### NFR-003: バンドルサイズ維持
- **要件**: JavaScriptバンドルサイズが現状の+5%以内であること
- **測定基準**: Next.js build outputのページバンドルサイズ

### 3.2 品質要件

#### NFR-101: テストカバレッジ
- **要件**:
  - 既存テストが全てパスすること
  - 新規コードのテストカバレッジが80%以上であること
  - ドメイン層は90%以上のカバレッジを目指す

#### NFR-102: 型安全性
- **要件**:
  - TypeScript strictモードで型エラーが0件であること
  - `any`型の使用を最小限に抑えること（やむを得ない場合を除く）

#### NFR-103: コード品質
- **要件**:
  - ESLintエラーが0件であること
  - Prettierフォーマットに準拠すること
  - 循環依存が存在しないこと

### 3.3 保守性要件

#### NFR-201: ドキュメント整備
- **要件**:
  - アーキテクチャ設計書の作成
  - ドメインモデル図の作成
  - 各レイヤーの責務を明記したREADME

#### NFR-202: レイヤー間の依存方向
- **要件**:
  - ドメイン層は他の層に依存しないこと
  - アプリケーション層はドメイン層のみに依存すること
  - インフラ層はドメイン層とアプリケーション層に依存できること
  - 依存性逆転の原則（DIP）を遵守すること

#### NFR-203: 単一責任原則
- **要件**:
  - 各クラス/関数が1つの責務のみを持つこと
  - 変更理由が1つであること

## 4. 技術要件

### 4.1 アーキテクチャ要件

#### TR-001: クリーンアーキテクチャの適用
- **要件**:
  - ドメイン層、アプリケーション層、インフラ層の明確な分離
  - レイヤー間の依存はインターフェースを介すること
  - ビジネスルールがフレームワークに依存しないこと

#### TR-002: DDDパターンの適用
- **要件**:
  - エンティティ: ビジネスルールを持つドメインオブジェクト
  - 値オブジェクト: 不変で置き換え可能なオブジェクト
  - リポジトリ: データ永続化の抽象化
  - ドメインサービス: エンティティに属さないビジネスロジック

#### TR-003: SOLID原則の遵守
- **要件**:
  - S: 単一責任原則
  - O: 開放閉鎖原則
  - L: リスコフの置換原則
  - I: インターフェース分離原則
  - D: 依存性逆転原則

### 4.2 データ要件

#### TR-101: 静的ファイルベースのデータ管理
- **要件**:
  - データベースを使用しないこと
  - 既存の`VideoMetadata`形式を維持すること
  - ビルド時に静的バンドルされること

#### TR-102: インデックスファイル形式維持
- **要件**:
  - `video-index.json`の形式が現状と互換性があること
  - インデックスの生成・検証スクリプトが動作すること

### 4.3 互換性要件

#### TR-201: 既存APIの後方互換性
- **要件**:
  - `src/lib/videos/video-data.ts`のエクスポート関数が変更されないこと
  - 既存の呼び出し元（pages、components）が修正なしで動作すること

#### TR-202: 段階的移行
- **要件**:
  - 4フェーズに分けて段階的に移行すること
  - 各フェーズで既存機能が破壊されないこと
  - フェーズごとにテストがパスすること

## 5. 制約条件

### 5.1 技術的制約

- **C-001**: データベースを使用できない
- **C-002**: Next.js 15のビルドプロセスに準拠する必要がある
- **C-003**: React Server Componentsとの互換性が必要
- **C-004**: 既存のテストフレームワーク（Jest）を使用する

### 5.2 ビジネス的制約

- **C-101**: 既存の動画データファイル（29本）の形式を変更できない
- **C-102**: `/videos`ページのダウンタイムを許容できない
- **C-103**: 開発期間は最大2週間以内

### 5.3 チーム的制約

- **C-201**: TDDアプローチ（t-wadaスタイル）を遵守する
- **C-202**: コミット前に全チェック（lint, format, type-check, test）が必須
- **C-203**: 日本語でのコメントとドキュメント作成

## 7. リスクと対策

### 7.1 技術的リスク

| リスク | 影響度 | 対策 |
|--------|--------|------|
| バンドルサイズの増加 | 中 | Tree-shakingの最適化、dynamic import活用 |
| パフォーマンス低下 | 高 | フェーズごとのベンチマーク実施 |
| 循環依存の発生 | 中 | madge等のツールで定期チェック |
| テストの破壊 | 高 | フェーズごとに全テスト実行 |
